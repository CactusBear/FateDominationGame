# 联机方案（P2P / 局域网 / 独立服务端）· 第三版

> 状态：P0 单机解耦与 P1 存档内核已实现；局域网、P2P 直连和多房间独立服务端均已在本机跑通正式 v2 完整对局，数据与卡图同步、私有待答、进程存活时的身份重连已有专项证据。批准文件大清单分片与 WebRTC 底层透明分帧已接通。普通主机存档菜单、独立服务端自动录制与原日志回放、服务端端内重新批准已有真实专项验证；房主崩溃恢复、死循环保护的全部原生边界及公网/Linux 验收仍未完成，不能视为整案交付。下文现状分析保留立项时快照；当前覆盖范围见各阶段进度文件，最新传输证据见 `docs/multiplayer-transfer-progress.md`。
> 第二版按以下已定口径修订：服务端支持多房间；做房主存档恢复；掉线不由 AI 托管；做观战。另外新增房间数据合并与卡图同步。
> 第三版追加口径：条目可选声明 `requires`；冲突不做优先级自动选择；死循环自动检测；临时数据默认缓存，客户端可清理；服务器任何人都能建房；观战默认「公共」且不加延迟；**服务端可以兼任 P2P 中继服务器**，负责信令交换和辅助打洞，不转发对局流量。P2P 不配中继时仍可只用邀请码，完全不依赖服务器。

## 0. 结论

1. **所有规则运算只在主机上进行。** 主机在局域网和 P2P 模式下是房主的游戏进程，在服务器模式下是服务端为该房间启动的子进程。客机只发送操作意图，接收按自身视角过滤后的视图；客机从不执行效果，也不掷随机数。
2. **三种模式只在建立连接的方式和主机的位置上有区别。** 大厅、数据同步、存档、观战和对局协议共用同一套代码。

   | 模式 | 主机 | 传输层 | 建立连接 |
   |---|---|---|---|
   | 局域网 | 房主游戏进程 | ENet（UDP） | 房主自选端口和绑定地址；局域网广播发现；也可手填 IP:端口，同一入口用于端口映射后的公网连接 |
   | P2P | 房主游戏进程 | WebRTC DataChannel | 两种握手方式：只用邀请码，完全不需要服务器；或填写一台开启中继职能的服务端，用房间码握手，并由它辅助打洞。对局流量始终直连，服务器不转发 |
   | 服务器 | 服务端为每个房间启动的子进程 | ENet | 客户端连接服务端唯一的对外端口，由服务端路由到具体房间 |

3. **不做帧同步。** 理由不变：游戏有隐藏信息；引擎使用全局随机数；卡牌游戏操作频率低，由主机逐条校验即可。
4. **最大的前置工作是 P0 解耦。** 要把 AI 推进和自动推进从 `battle_board_v2.gd` 中拆出来，并把界面对引擎的约 40 种写调用收拢到一个指令门面。服务端没有界面，存档又需要逐条记录主机上的写操作，所以这一步无法绕开。

### 2.2 意图与视图协议

- **意图格式**：`{v, seq, kind, args}`。参数只允许基础类型和网络 ID，RPC 保持 `allow_objects = false`。
- **意图校验**按顺序做三步：
  1. 发送者的 peer 是否对应这个座位；
  2. 这个座位当前是否应该行动，或者是否有等待它的输入；
  3. 调用与单机**相同的**引擎入口，以返回值决定是否接受。

  主机不另写一套规则判定。
- **视图**：v1 在每次状态变化后，给每个观察者发送一份全量视图，另附事件流用于播放动画。
  - 界面需要的可操作提示由主机用现有判据计算后附在视图里，包括金框、明置/暗置按钮、可发动的效果、可选目标和费用预览。
  - 悬浮时的威力预览走单独的查询 RPC，不改变任何状态。
- **随机数**：主机在对局开始时生成 `match_seed`，调用 `seed()` 并写入存档。客机上不存在随机来源。

## 3. 三种连接模式

### 3.1 局域网

- **建房参数**：
  - 游戏端口：默认 24680，范围 1024–65535。
  - 发现端口：默认 24681，可修改，也可关闭发现。
  - 绑定地址：`*`、`0.0.0.0`、某张网卡的 IP，或 IPv6 的 `::`。
  - UPnP 自动映射：开关，默认关闭。映射失败只给提示，不阻止建房。
- **端口被占用**：直接报出端口号，不自动换端口，否则已经配好的端口映射会失效。
- **手动连接**：支持 `IP:端口`、域名和 `[IPv6]:端口`。房间页提供「复制本机地址」，列出所有网卡 IP 加当前端口。

### 3.2 P2P

所有对局数据都在房主与客机之间直连传输，**任何服务器都不转发游戏流量**。打洞失败就是连接失败，界面会说明原因并给出改用其他方式的建议。建立连接有两种方式，由房主建房时选择：

| | 邀请码 | 中继服务器 |
|---|---|---|
| 需要服务器 | 不需要 | 需要一台开启 `relay` 职能的服务端（见 3.3） |
| 握手 | 每名加入者与房主手动往返一轮邀请码 | 输入「服务器地址 + 房间码」，信令自动交换 |
| 打洞辅助 | 只有公共 STUN | 中继服务器提供地址反射、增量交换候选、协调双方同时发包，成功率更高 |
| 打洞失败 | 报告失败原因 | 同左，不改走服务器转发 |
| 主机 | 房主 | 房主。中继服务器只参与握手，连上之后它离线也不影响对局 |

#### 3.2.1 共用细节

- **拓扑**：星型。每个客机与房主之间建立一条 DataChannel，房主是 peer 1。
- **STUN**：地址列表写在配置里。本机实测 `stun.miwifi.com` 和 `stun.chat.bilibili.com:3478` 可达，Google 和 Cloudflare 的 STUN 不通，所以默认列表把国内可达的放在前面。使用中继服务器时，它自带的地址反射排在列表最前。
- **失败诊断**：界面写明失败发生在哪一级，例如 STUN 不可达、没有可配对的候选、双方都是对称型 NAT、超时，并建议改用局域网端口映射或服务器模式。
- **界面**：每个座位显示 ping 和连接类型，例如「局域网直连」或「打洞直连」。

#### 3.2.2 邀请码方式

1. 房主点击「生成邀请」，得到邀请码 A：内含房间 ID、一次性 peer 槽、SDP offer 和完整的 ICE 候选，压缩后用 base64 编码，并带过期时间。
2. 加入者粘贴 A，得到应答码 B。
3. 房主粘贴 B，连接建立。

- WebRTC 必须双向交换信息，所以每名加入者都需要这一轮往返。
- 邀请码可以通过任意聊天软件传递。过期或已被使用的码会明确提示。
- 因为没有信令通道可以中途补发，要等 ICE 候选全部收集完才生成邀请码，不做增量推送。
- 观战和中途重连同样需要交换一轮邀请码。

#### 3.2.3 中继服务器方式

- **登记**：房主连上中继服务器并登记房间，拿到短房间码，码长和有效期由服务器配置。房主与服务器之间保持一条轻量信令连接，用于接收新的加入请求。观战和重连同样只需要房间码。
- **地址反射**：中继服务器自己就是一个 STUN 端点，返回请求方的公网地址和端口，不依赖第三方 STUN 是否可达。可以开第二个端口，用于判断 NAT 类型（锥型还是对称型），这样在打洞前就能预判成功率并提示用户。
- **增量交换候选**：SDP 和 ICE 候选通过服务器实时转交，收集到一条就发一条（trickle ICE），比邀请码方式更快建立连接。
- **协调同时发包**：ICE 的连通性检查本来就是双方同时互相发包，中继服务器负责把一方的候选即时转给另一方，让双方几乎同时开始检查，避免一方先发、另一方的 NAT 映射却已经过期。这一点在端口受限型 NAT 下最有用。双方都是对称型 NAT 时，打洞基本不可能成功，界面会直接说明这种情况。
- **只转交握手信令**：信令内容是 SDP 和候选，不含任何对局数据；连接建立后，对局数据走 DataChannel，由 DTLS 加密，服务器既看不到也不经手。
- **中继服务器离线**：已经建立的连接不受影响；只是新加入和重连暂时做不了。房主可以在房间里换一台中继服务器重新登记，也可以临时改用邀请码。
- **防滥用**：按配置限制单个 IP 可以登记的房间数、每秒信令消息数和房间码查询频率。

### 3.3 独立服务端（多房间）

- **产物**：同一工程以 Dedicated Server 方式导出，得到 `FateServer.exe` 和 `FateServer.x86_64`。
- **启动**：Windows 下运行 `FateServer.exe --headless -- --config server.cfg`，Linux 同理。首次启动会生成带注释的 `server.cfg`，以及空的 `ops.json`、`banned.json`、`whitelist.json`。
- **进程结构**：一个主进程，加上每个房间各一个子进程。

  ```
  客户端 ──唯一对外端口──▶ 主进程（网关）
                            ├ 连接、身份、封禁与白名单、服务器级房间列表、控制台
                            ├ 按房间 ID 把消息转发给子进程（不解析对局意图，只加上 peer→座位 的信封）
                            └ 子进程管理：启动、心跳、崩溃后从存档重启、回收空房
  房间子进程 = 同一个可执行文件加 --room-worker 参数，只监听 127.0.0.1
                            └ 也就是「无界面的主机」：MatchDriver + DataHub + MatchJournal，与房主进程同一份代码
  ```

- **为什么不在一个进程里跑多个房间**：那需要把 12 个被引用数百处的单例全部改造成按房间区分的上下文，改动面最大，风险也最高。子进程方案还带来三点好处：
  - 每个房间可以加载各自不同的合成数据；
  - 客机数据引起的死循环或崩溃只影响自己的房间；
  - 崩溃后可以从存档单独重启。
- **`server.cfg` 主要字段**（代码里不写死任何值）：

  | 段 | 字段（括号内为默认值） |
  |---|---|
  | `[server]` | `bind_address`（`*`）、`port`（24680）、`server_name`、`motd`、`password`、`whitelist`、`roles`（`["game", "relay"]`，可以只填其中一个；只开 `relay` 时就是一台纯 P2P 中继服务器） |
  | `[relay]` | `room_code_length`（6）、`room_code_ttl_sec`、`reflect_port`（地址反射端口）、`reflect_port_alt`（判断 NAT 类型用的第二端口，0 表示关闭）、`ice_timeout_sec`（单次打洞的超时）、`stun_servers`（下发给客户端的备用 STUN 列表）、`rooms_per_ip`、`signal_rate_limit` |
  | `[rooms]` | `max_rooms`（8）、`who_can_create`（`anyone`，可选 `ops`/`console`）、`empty_room_ttl_sec`（300）、`worker_restart_limit`（3）、`worker_port_range` |
  | `[room_defaults]` | 选人模式、座位数、AI 数、数据来源模式、观战席、限时 |
  | `[data]` | `server_data_dir`（服务器自己的 data，即「主机 data」）、`max_entry_mb`、`max_room_data_mb`、`max_image_pixels`、`allowed_ext`（`json`、`png`、`jpg`、`webp`） |
  | `[match]` | `turn_timeout_sec`（0）、`disconnect_policy`（`wait`，见 4.5）、`intent_rate_limit` |
  | `[save]` / `[log]` | `dir`、`keep_days` |

- **控制台**：输入进程与网关进程分离，stdin 等待不会阻塞网关；通过管理员显式启用的本机目录交换带服务实例标识的请求与响应，网关主线程执行注册式白名单命令。此实现替代原先阻塞读线程方案，避免平台读线程取消与退出回收问题；不得把本机通道注册为未经认证的远程入口。
  - 全局：`help`、`status`、`stop`、`reload`、`say`、`list`、`kick`、`ban`/`pardon`（按 UUID 或 IP）、`op`/`deop`、`whitelist ...`
  - 中继：`relay status`（列出登记的房间、握手成功和失败的次数、各 NAT 类型的占比）、`relay close <房间码>`、`relay limit <键> <值>`
  - 房间：`rooms`、`room create`，以及 `room <id> info|close|save|set <键> <值>|kick <名>|seat <n> ai|open|close`
  - 对局：`room <id> pause|resume|log [n]|seed`
  - `stop`、Ctrl+C 和 SIGTERM 的行为相同：先通知所有房间结算完当前这一步，存档写盘后再退出。
- **身份**：客户端生成并本地保存密钥，以服务端验证过的公钥指纹识别身份，不信任自报 UUID。登记无需管理员逐人批准，未启用白名单即允许普通登记；启用白名单按密钥身份授权。登记附带用户名及昵称：用户名区分大小写，最多 32 字符，仅英文字母、下划线和数字且不能数字开头；昵称允许重复。用户名允许修改但密钥不变，原权限、白名单及封禁仍绑定同一密钥身份。用户名占用检查与写入必须原子执行。此段是已确认规格，不表示认证接线已完成。

### 3.4 服务端配置与运行时控制台待办

#### 配置接入顺序

## 4. 大厅

### 4.1 状态机

```
InLobby ⇄ DataSync ──全员同步 + 验证通过 + 准备──▶ Selecting ──▶ InMatch ──▶ PostMatch ──▶ InLobby
   ▲                                                   │ 取消                 │ 主机崩溃 / 房主掉线
   └───────────────────────────────────────────────────┘                      ▼
                                                                       Suspended（存档已落盘，等待恢复）
```

### 4.2 房间设置（房主可改，其他人只读）

| 项 | 约束 |
|---|---|
| 联机模式 | 建房时确定，之后只展示 |
| 选人模式 | 读取主机的 `selection_modes.json`。该文件包含 `res://` 脚本路径，因此不参与客机数据合并 |
| 座位数 | 1 到 `capacity()` 之间。容量按当前合成数据计算，勾选的数据变化后立即重算 |
| AI 数量 | 0 到「座位数减去真人数」之间 |
| 数据来源 | 「仅主机数据」或「合并客机数据」，详见第 5 节 |
| 观战 | 席位上限（0 表示关闭）、可见范围、延迟 |
| 限时、掉线处理、密码 | 与 `server.cfg` 共用同一份字段定义 |

容量下降到低于当前座位数时，不自动踢人，而是禁止开始，并提示「容量 N，当前 M 人」。

### 4.3 座位与权限

- **座位状态**：空位、真人、AI、关闭。真人座位显示准备状态、同步进度、ping，掉线时显示倒计时。
- **房主可以**：
  - 踢出、封禁、转让房主；
  - 把座位设为 AI、空位或关闭；
  - 调整大厅展示顺序（开局顺位仍由 `get_initial_order()` 决定）；
  - 修改设置、管理数据、开始游戏、解散房间；
  - 把掉线玩家判为出局，或作废本局。
- **房内玩家可以**：准备、改昵称、聊天、离开、申请换座；在大厅阶段于玩家与观战者之间切换；设置本机愿意共享哪些数据。
- **开始条件**（全部满足才可开始）：
  - 所有真人都已准备；
  - 人数达到选人模式声明的下限；
  - 没有未解决的数据冲突；
  - 合成数据验证通过；
  - 所有人（包括观战者）完成数据同步。
- **数据集合一旦变化，清空所有人的准备状态。**
- **服务器模式下房主离开**：按配置移交给最早加入的真人，或改由控制台管理；房间子进程不受影响。
- **局域网 / P2P 模式下房主离开**：大厅阶段直接解散房间；对局中进入 Suspended 状态，按第 6 节恢复。

### 4.4 选人联机化

- 选人会话放在主机上。意图是 `choose_master{template_name}`，由主机查表。
- AI 座位用 `DummyBot.pick_master` 选择。这是 AI 座位在给自己选阵容，不算托管。
- 真人座位**只能等待本人选择**。可以配置选人限时，到时后也不代选，而是暂停，由房主决定继续等待，还是把该座位改为空位或关闭后重新选人。
- 隐私口径不变：每个客机只收到自己的从者，共用界面只显示「分配完成」。

### 4.5 掉线（不做 AI 托管）

- 玩家掉线后，座位标记为「已掉线」并开始倒计时。任何决策都不交给 AI。
- 不需要掉线者输入的推进照常进行。一旦轮到他行动，或者有等他做的选择，**整局暂停**，所有人都能看到「等待 某某」和已掉线时长。
- 战斗播报确认只是展示确认，不涉及规则决策，所以默认把掉线者视为已确认，避免全场卡住。配置项 `broadcast_skip_disconnected` 可以关闭这一行为。
- 宽限期结束后，按 `disconnect_policy` 处理：
  - `wait`（默认）：继续等待，房主随时可以手动处理；
  - `forfeit`：自动判为出局，复用现有的 `is_out` 流程。

  两种策略下，房主都可以手动执行「判为出局」或「作废本局」。
- **重连**：凭房间 ID、UUID 和会话 token 重新连接，主机下发全量视图和最近若干条可见事件。客机把重连信息保存在 `user://`，即使客机崩溃重启也能回到房间。

### 4.6 观战

- 观战者不占座位，也不计入容量；人数上限可配置，0 表示关闭观战。
- 可见范围由房主设置：
  - 「公共」（默认）：只看到公开信息；
  - 「全知」：能看到所有手牌和暗置牌，开启时界面会提示作弊风险。

  另可设置延迟，按事件条数或秒数计。
- 观战者同样需要同步数据才能显示卡图。可以在对局中途加入观战，加入时主机下发全量公共视图。
- 玩家出局后可以转为观战，看到的是公共视图加上自己原有的私有信息。
- 观战者的聊天是否对玩家可见，可以配置。

## 5. 房间数据：合并客机数据与卡图同步

### 5.1 条目与清单

- **条目**：`data/` 下各类别目录中，一个 JSON 所在的目录算一个条目，条目连同里面的全部图片一起移动。
  - 类别直接取顶层目录名：`masters`、`servants`、`events`、`situations`、`attacks`、`command_spells`、`card_backs`。分类依据是目录结构的显式声明，不从内容推测。
  - `selection_modes.json` 和生成文件 `tag_list.json` 不算条目。
- **清单**：每个参与者加入房间时只上报**清单**，不上传内容。清单的每一项包括：
  - 类别；
  - 模板名，取自 JSON 中的显式名称字段，如 `_name`、`card_name`；
  - 显示名；
  - 相对路径；
  - 每个文件的路径、大小和 sha256。
- **共享设置**：玩家可以在本机关闭某些条目，被关闭的条目不出现在上报的清单里。
- **依赖声明 `requires`**（可选字段，写在条目 JSON 的顶层）：
  ```json
  "requires": [
    {"category": "attacks", "query": "strength:2"},
    {"category": "attacks", "name": "avenger_class"}
  ]
  ```
  - 有两种写法。`name` 按「类别 + 模板名」引用；`query` 写的是牌库构成串，例如 `strength:2`，由验证器按 `LoadAttack.resolve` 的同一套规则解析，与牌库的实际语义保持一致。两种写法都不绑定版本。如果被依赖的条目有冲突，按 5.3 的规则由房主选择来源。
  - 清单上报时带上 `requires`。勾选某个条目时，列出它尚未勾选的依赖，提供「一并勾选」；取消勾选一个被其他条目依赖的条目时，提示哪些条目会因此缺少依赖。
  - 依赖在房间所有可用数据中都找不到时，该条目标记为「缺少依赖」，并禁止开始。
  - 依赖关系可以成环，例如 A 和 B 互相依赖，勾选时一次性列出整个闭包。
  - 没写 `requires` 的条目，程序不推断它依赖什么，只靠 5.5 的加载验证发现缺失。
  - 主机的通用卡背（`data/card_backs`）和通用令咒构成房间的**基础集合**，所有条目都可以直接使用，不用另外声明。
  - 现有 data 的补写方案见 `docs/multiplayer-requires-proposal.md`，确认之后再写入。

### 5.2 两种数据来源模式

| 模式 | 主机运算使用的数据 | 客机得到的数据 |
|---|---|---|
| 仅主机数据 | 主机的 data（服务器模式下为 `server_data_dir`）；房主也可以取消勾选其中部分条目 | 同一份合成数据，包括 JSON 和全部卡图，下载到临时目录 |
| 合并客机数据 | 主机 data 加上房主勾选的客机条目 | 同上 |

- **勾选粒度是单个条目**：单个从者、御主、事件卡、攻击牌等可以任意组合，不要求加入某个玩家的全部数据，也不要求按类别整批加入。
- **批量操作**：可以按玩家、按类别或按搜索结果全选或全不选；也可以整体开关某个玩家的贡献。
- **客机始终只用房间的合成数据**，不混用本机 data。这样可以避免同名但不同版本的条目在客机界面上的显示与主机运算不一致。

### 5.3 冲突与去重（不靠猜测）

| 情况 | 处理 |
|---|---|
| 同类别、同模板名，所有文件哈希一致 | 视为同一条目，自动去重，并记录所有提供者 |
| 同类别、同模板名，内容不同 | 标记为**冲突**，房主必须为它选定一个来源，未解决前禁止开始。可以用「冲突全部采用某人」一键处理，但必须由房主手动点击，不设隐含的默认值 |
| 模板名不同但目录名相同 | 不算冲突。组装时每个来源各放一个子目录，路径互不相同 |
| `card_backs` 中的同名卡背 | 按冲突处理，由房主选一个 |
| 显示名相同但模板名不同 | 不算冲突，只给出提示 |
| 两张以上攻击牌能匹配同一个牌库查询，例如 `strength:7` | 按冲突处理，由房主选定：`属性:威力` 是一次查询，客机加入新牌后，查询结果可能悄悄改变 |

### 5.4 传输与临时目录

- **数据流向**：一律经过主机。提供者先把文件发给主机，主机校验哈希后保存，再分发给其他人。主机收齐之后，提供者离开也不影响本局。
- **分块传输**：走独立通道 2，块大小可配置（默认 64 KB）。每块都校验，支持断点续传，限速可配置，不会阻塞对局消息。
- **按内容寻址**：以 sha256 为键。本机已有同一哈希的文件时直接复用，不重复下载；例如客机本地已有与主机完全相同的基础卡，就不必再传。
- **临时目录**：`user://net_session/<room_id>/data/`。组装后的结构是 `data/<类别>/<来源前缀>/<原目录>/`，正是加载器期望的结构。根目录名必须保留为 `data`，因为现有的递归扫描依赖这个名字。
  - 离开房间时删除该目录。
- **缓存（默认开启）**：下载过的文件按 sha256 存放在 `user://net_cache/blobs/` 下，下次进任何房间遇到相同的文件都直接复用。
  - 上限默认 2 GB，可修改，也可设为不限。超出上限时，按最近使用时间淘汰最久没用到的文件。
  - 客户端的「设置 → 联机缓存」页面显示占用空间和文件数，提供「清理全部」和「清理 N 天前的文件」两个操作。
  - 当前房间正在使用的文件会被跳过，不会被清掉，并提示跳过了多少。
  - 缓存只是加速。缓存被清空或损坏时（哈希校验失败），会从主机重新下载，不影响正确性。
  - 存档自带 blob，所以清理缓存不影响恢复存档。
- **数据冻结**：从开始选人起，数据集合不再变化，这与现有「开局后不热替换角色」的口径一致。主机也会把合成数据组装到会话目录，并通过数据根目录覆盖来加载；离开房间后恢复本机数据并重新加载。
- **进度显示**：每个座位和观战者旁边显示进度条和速率，房主可以踢出卡在同步中的人。

### 5.5 安全与验证

- **文件过滤**：
  - 只接受白名单中的扩展名。
  - `.import` 文件一律丢弃（`load_texture` 本来就能在运行时读取图片）。
  - 以下情况直接拒绝：路径穿越（含 `..` 或绝对路径）、超出大小上限、图片像素超限或无法解码、JSON 无法解析或嵌套层数超限。
- **加载验证**：用子进程 `--validate-data <目录>` 在 headless 下实际加载合成数据，有超时限制，最后输出错误报告。检查内容包括：
  - JSON 错误；
  - **未知的 `func_name`**（现在是静默跳过，验证时必须报错）；
  - 模板重名（与现有 `roster_catalog` 的检查相同）；
  - 图片缺失；
  - 选人模式容量。

  使用子进程有两个原因：不污染主机进程的状态；加载卡死时可以直接杀掉。
- **版本一致性**：加入房间时要求协议版本和 **operation 表哈希**（`AllOperations.TABLE` 键集合的哈希）一致，不一致就拒绝并列出差异。数据不同不会被拒绝，因为数据由房间负责同步。

## 6. 存档与恢复

### 6.1 存档内容（追加写，每条记录都立即落盘）

1. **文件头**：协议版本、operation 表哈希、房间设置、座位（UUID 与 player_id 的对应关系）、`match_seed`、选人结果，以及本局的数据清单和全部 blob。存档自带数据，所以即使提供者日后删掉了数据也能恢复。
2. **记录**：主机上所有改变规则状态的操作，按发生顺序写入，包括：
   - 真人意图；
   - AI 的每一步，记为 `ai_step(bot_id)`；
   - 驱动器的自动推进，如无需输入时自动结束；
   - 房主的管理动作，如判为出局。
3. **检查点**：每隔 N 条记录保存一次 `capture_rule_state()` 的哈希。

### 6.2 恢复方式：重放

- **为什么不直接序列化对象图**：对象图中有 RefCounted、弱引用和 Callable，完整序列化的工作量和出错风险都远大于重放。重放只依赖 P0 的门面和固定的随机种子。
- **校验**：重放时，每到一个检查点就比对状态哈希。一旦不一致立即停止，并报告「存档在第 K 条记录处无法复现」，不带着错误的状态继续。
- **确定性前提**：
  - 主机的随机数只来自 `seed(match_seed)` 之后的全局随机数生成器；
  - 界面层不使用随机数，并补一条 grep 守卫测试，防止以后被引入；
  - 推进时机全部记录在存档里，不依赖帧率。

### 6.3 恢复流程

- **局域网 / P2P（房主恢复）**：
  1. 房主重启游戏，在联机中心选择「可恢复的对局」。
  2. 局域网用原端口重新建房；P2P 中继方式到中继服务器重新登记，沿用原房间码，原房间码已过期时生成新码；P2P 邀请码方式为每个座位重新生成邀请码。
  3. 主机在后台重放到最新一条记录，此时所有真人座位都处于「已掉线」状态。
  4. 局域网客机按保存的地址自动重试连接；P2P 中继方式的客机按保存的房间码自动重试；P2P 邀请码方式的客机需要粘贴新的邀请码。
  5. 全员回来后继续；也可以由房主把一直没回来的人判为出局。
- **服务器**：房间子进程崩溃后，主进程自动从存档重启它，次数受 `worker_restart_limit` 限制，客户端只会看到一次短暂的重连。服务器整体重启后，Suspended 状态的房间同样可以恢复。

## 9. 极端情况清单（实现时逐条写断言）

1. 端口被占用或越界、绑定地址不存在、IPv6、发现端口与游戏端口相同、同机多开。
2. 协议版本或 operation 表不一致：拒绝加入并列出差异。
3. 客机数据引用了主机没有的 operation：验证时报错并阻止该条目，绝不静默跳过。
4. 同名不同内容：未解决前禁止开始；同名同内容：去重。
5. 恶意数据：路径穿越、超大文件、解码炸弹、非白名单扩展名、深层嵌套的 JSON、伪造哈希（主机重新计算后与声明不符）。
6. 提供者在同步途中掉线：只有他持有、且主机尚未收齐的条目标为不可用，由房主决定移除还是等待。
7. 数据勾选导致容量变化：禁止开始，不踢人；勾选变化后清空所有人的准备状态。
8. 客机数据导致主机死循环：按第 10 节自动检测并交由房主处理。服务器模式的子进程另设看门狗兜底。
9. 选人或行动阶段有人掉线：暂停等待，不代为决策。服务器模式下全部真人都掉线时，房间保留一段时间后存档并挂起。
10. 对局中途加入观战；观战人数达到上限。
11. 存档重放与原局不一致：停止并报告是第几条，不带错继续。存档损坏或被截断：恢复到最后一条完整记录，并提示可能丢失的部分。
12. P2P 邀请码过期、被重复使用、贴错房间；房间码不存在或已过期；同一 IP 刷房间码查询；中继服务器在握手途中断开。
13. 服务端执行 `stop` 时有效果正在结算：等这一步结算完、存档写盘后再退出。
14. 倒计时只在主机上计算，客机只显示主机下发的剩余秒数，修改客机系统时间无效。
15. 意图重复到达时按 `seq` 去重。伪造他人座位或高频刷意图的请求一律拒绝并记录，累计次数达到配置值时自动踢出。

## 10. 死循环自动检测

### 10.1 能做到什么

能做，但要先说清楚边界：

- **能确定**：任何「状态完全重复」的死循环都能自动认出来，并且不会误报。引擎在主机上的运行是确定的，同一个完整状态必然走出同一个后续，所以只要完整状态重复出现，就证明会永远绕圈。
- **不能确定**：在每一圈都改变状态的无限循环。例如每圈给威力加 1，状态永远不会重复，在理论上无法和「一次计算量很大但会结束的结算」区分开（停机问题）。这一类只能用「疑似」处理，最终由房主判断，不靠程序猜测后直接中止。

### 10.2 检测的范围与入口

「一次结算」指从主机接受一条意图（或 AI 的一步、自动推进的一步）开始，到引擎停下来等待输入或回到空闲为止。死循环只可能发生在一次结算内部，检测只在这个范围内进行，并且接在以下现有循环点上：

| 循环点 | 位置 | 检测方式 |
|---|---|---|
| 效果流水线 | `EffectManager.run_pipeline` 中的 `while true`、`resolve_one` | 计步，并做状态重复检测 |
| 一条效果内部的步骤 | `_continue_run` 中的 `while` | 计步 |
| 时点连锁 | `run_time_point` 在 `is_running` 时追加效果 | 计入同一次结算的步数 |
| 递归嵌套 | `activate_effect` → `_continue_run` → `_ask_next_choice`，以及 `run_func_descriptor` 的嵌套调用 | 嵌套深度检测 |
| 循环 op | `WhileFunc` 已有 `max_iterations`（缺省 1000，保持现状不改）；`ForeachFunc` 遍历的数组是有限的 | 每一圈计步 |

### 10.3 三层检测

1. **状态重复（确定的死循环）**
   - 一次结算的步数超过「观察起点」后，每结算一个效果，就计算一次签名：`capture_rule_state()` 的哈希，加上待决队列、结算池、暂停中的运行及其步骤下标、已排队的时点批次，再加上全局随机数生成器的当前状态。
   - 用 Brent 环检测算法比较签名，只需保存常数个签名。
   - 签名重复，就判定为死循环，同时可以得到环的长度和环内依次结算的效果。
   - 观察起点是性能开关，不是规则数字，可以配置，默认 200 步：签名有开销，短结算不需要计算。
2. **嵌套深度（防止进程直接崩溃）**
   - 递归嵌套太深会让 GDScript 栈溢出，导致整个主机进程崩溃，连存档都来不及处理。
   - 深度上限从工程设置 `debug/settings/gdscript/max_call_stack` 读取（实现时核对实际键名），再留一段安全余量，不另写一个固定数字。
   - 接近上限时立即停住，按「疑似」处理。
3. **长时间未结束（疑似）**
   - 一次结算的耗时超过配置值（默认 3 秒，服务器和房主可以修改），并且没有被认定为状态重复时，暂停结算，交给房主决定。
   - 暂停是协作式的：在上面的每个循环点上检查耗时。结算在哪一步暂停，以「步号」为准写入存档，而不是以时间为准，所以重放时会在同一步停住，结果保持确定。

### 10.4 检测到之后

- **大厅保留预算设置，对局后台检查**：不在战局常驻展示步数、耗时或预算原因。达到协作预算只能称疑似异常，不把长结算直接判为确定死循环。
- **结算暂停后才提示**：房主看到所属玩家、来源牌和具体效果，其他玩家与观战者只看到等待房主处理，不收到隐藏卡牌诊断。生成的待答子效果缺少自身来源牌时，通过原效果事务的显式根对象追溯，不按牌名猜测。
- **由房主选择跳过或重开**：

| 选项 | 做法 | 适用情况 |
|---|---|---|
| **跳过** | 回退整个来源效果及其引发的连锁到发动前，再继续原生外部流程。不能保留已经生效的资源、移牌、待答、日志或随机副作用 | 有有效完整检查点时 |
| **当前阵容重开** | 从批准模板重建已选御主、从者与顺位，保留原随机种子，不复用已释放对象 | 已保存完整开局阵容时 |
| **返回大厅重新选人** | 保留连接、成员和批准数据，清除准备、旧待答与战局视图，重新准备、选人并开始 | 正在进行的联机房间 |

- **回滚边界**：注册的子效果、跨玩家答复与效果内部延迟尾部继承同一根事务。原生调用者在效果外登记的尾部保留，完成回滚后只运行一次。旧待答、旧视图重发必须被拒绝。
- **无法完整恢复就拒绝跳过并保留暂停现场**：未知随机、失效对象、采集预算不足及尚未支持恢复的类型均不能冒充成功。回滚只在同一权威进程内原地恢复，不执行来自网络或存档的对象与 Callable。
- **重开不自动删除或停用数据**：数据变更仍由房主在大厅显式选择并经过批准、验证与同步流程，不删除任何人本机文件。
- **单机**：保护与处理入口仍需独立接线验收，不能把联机房主窗口测试当作单机已完成。

### 10.5 开局前检测

**结论：可以检测，而且会作为开局前的必经步骤，但检测通过不等于证明对局中一定不会出现死循环。**

原因有两点：
- 一次结算会不会无限循环，取决于对局中的具体状态：场上有哪些牌、玩家做了什么选择、随机数抽到什么。开局前无法穷举所有状态。
- 任意规则组合是否会停机，在理论上不可判定。

所以开局前检测负责**尽量提前发现问题**，第 10.3、10.4 节的运行时检测保留，作为兜底。

开局前检测分三层，都放在 5.5 节的验证子进程里运行，不污染主机进程：

1. **静态检查**：只读数据，几秒内完成。
   - 画出触发图：节点是效果，边是「效果 A 会派发时点 T，而效果 B 监听 T」。派发时点的信息取自 op 参数里显式写出的时点名，例如 `dynamic_time_point`、`schedule_effect_on_time_point` 的时点数组。参数由变量计算得出、无法静态确定时，记为「未知」，不去猜测。
   - 列出图中所有环，并标注每个环上是否有「每回合 / 每局次数上限」（`max_total_uses`、`reset_counts_each_round`）或已经结算过的标记。没有任何限制的环标为**高风险**，有限制的环标为**低风险**。
   - 检查 `while_func`：把 `max_iterations` 写到异常大的，或者条件恒为真的，标出来。
   - 检查自我重排：`schedule_effect_on_time_point` 在被安排的效果里又安排了自己，并且没有设置到期时点（`expire_time_points`）的，标出来。
2. **聚焦模拟**：只针对高风险环。
   - 用合成数据开出无界面的全 AI 对局，强制让环上的条目登场，例如把这些从者或御主分配给 AI 座位，把相关的事件或局势牌排到牌库顶。
   - 运行时 `LoopGuard` 全程打开，跑若干回合。
3. **随机模拟**：覆盖静态检查漏掉的情况。
   - 在时间预算内，用不同的随机种子和不同的阵容组合跑全 AI 对局。AI 的选择也随机化，以覆盖更多分支。
   - 有独立开关 `random_sim_enabled`，默认开启。局数和时间预算 `random_sim_budget_sec` 可以配置，默认 60 秒，跑满局数或用完时间就停。预算设为 0 秒时一局也不跑，效果与关闭开关相同，但开关和预算是两个独立的设置项。房间设置和 `server.cfg` 的 `[data]` 段都提供这两项。

**结果与处理**：

| 结果 | 处理 |
|---|---|
| 模拟中触发**确定死循环**（状态重复） | 禁止开局，报告环中的效果和所属条目，并附上能复现的随机种子与阵容。房主可以一键取消勾选这些条目，然后重新检测 |
| 模拟中触发嵌套过深或长时间未结束 | 不禁止开局，作为警告交给房主决定 |
| 静态检查发现高风险环，但模拟中没有触发 | 只提示，不阻止 |
| 全部通过 | 显示「未发现死循环」，同时写明本次覆盖情况：跑了多少局、多少回合、模拟中实际触发过哪些效果、哪些效果一次都没有触发 |

**缓存**：检测结果以「合成数据的哈希 + operation 表哈希」为键缓存下来。数据组合不变时，再次开局不需要重新检测。

**单机**：载入新数据或修改过的数据后，同样可以在本地手动运行一次。

### 10.6 对引擎的改动范围

- 计步、签名、深度检测和协作暂停只加在 10.2 列出的循环点上，不改任何 operation 的语义。
- 检测逻辑放在独立的 `LoopGuard` 中（单一职责，只回答「继续、暂停、判定」）；`EffectManager` 只在循环点上调用它。
- 签名与存档的检查点哈希都复用 `capture_rule_state()`，不另写一套状态提取。
- 开局前检测复用同一个 `LoopGuard`，再加上 P0 的无界面 `MatchDriver`。模拟对局与真实对局走同一套代码，不另写一个规则模拟器。
- 回归要求：
  - 现有全量测试中，正常结算一次都不能触发检测。
  - 另写构造用例，分别覆盖：互相触发的确定环、每圈加威力的发散环、深度递归、`WhileFunc` 次数耗尽。
  - 开局前检测必须能找出这几个构造环：对确定环禁止开局，对其余两类给出警告。

## 11. 已定口径

- **`requires`**：要做。现有 data 按 `docs/multiplayer-requires-proposal.md` 的建议补写：
  - A 类牌库引用，写成查询形式；
  - B 类按名字查询的引用，不写入；
  - C、D 类的通用卡背和通用令咒，作为房间基础集合。
- **冲突**：不做优先级自动选择。
- **死循环**：开局前与对局中都检测（第 10 节）。
  - 「疑似」的判定阈值默认 3 秒。
  - 大厅保留预算设置，对局中后台检查，异常时房主看到玩家、来源牌与效果，选择完整回滚跳过或重开。重开可选择当前阵容或返回大厅重新选人；其他人只看等待，不收到隐藏诊断。
  - 开局前的随机模拟有独立开关，默认开启，默认预算 60 秒。
- **缓存**：默认开启，客户端可自行清理。
- **建房**：服务器上任何人都可以建房。
- **观战**：默认「公共」，不加延迟。
- **服务端兼任 P2P 中继服务器**：只辅助打洞，不转发对局流量。

P0 已按确认范围完成：独立驱动器、座位控制表、本地指令门面与 v2 接线。AI 步骤持久化、规则状态完整序列化与联机权限尚未实现，属于后续阶段，不能把 P0 的抽离当作这些能力已经具备。
