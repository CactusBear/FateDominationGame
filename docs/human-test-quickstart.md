# 真人测试包：启动与反馈

> 本包是 `HUMAN_TEST_CANDIDATE`，不是正式发行版，未做全量认证。下面按当前源码入口静态核对，不代表最终 EXE 已运行通过；请同时查看包内 `known-limitations.json` 与 `phase-runformal.json`。

## 启动哪个程序

路径均相对解压后的包根目录；完整解压，不要单独移动 EXE、PCK、`data/` 或原生依赖。

| 程序 | 用途 | 同机最小测试是否手动启动 |
| --- | --- | --- |
| `client/START-CLIENT.cmd` | 玩家界面；双击启动脚本，不直接双击 `FateDomination.exe` | 是，两个独立身份的客户端 |
| `server/START-SERVER.cmd` | 独立游戏服务启动脚本：管理房间，启动执行规则和保存对局的权威子进程 | 否；局域网房主客户端自行管理本机权威子进程 |
| `signaling/START-SIGNALING.cmd` | 信令启动脚本：为「房间码直连」交换连接信息；不运行规则、不保存对局、不转发游戏流量 | 否；「局域网」模式不用信令 |

若包只包含 client，不需要寻找另两个目录。仅测试同机局域网不需要公网地址、路由器映射或 STUN。

## 同一台 Windows 电脑，两个客户端

**用脚本隔离身份目录**：启动脚本调用同目录的 `Launch-HumanTest.ps1`，将本次进程及其子进程的 `APPDATA`、`LOCALAPPDATA`、`TEMP`、`TMP`、`TMPDIR` 隔离到包下 `test-users/<身份或角色>/`，不修改系统永久环境变量。包须解压到非系统盘、非 UNC、无目录链接的位置。客户端双击 `START-CLIENT.cmd` 后按提示选 `host` 或 `guest`；双开时分别选这两个身份目录，同一身份目录不能代替两个独立身份。服务端和信令分别使用 `server`、`signaling` 目录。

同一 Windows 用户直接双开 EXE 会共用 `user://net_identity/`；改昵称或复制 EXE 不等于新身份。也可使用以下两个独立 CMD 窗口，每个窗口先进入同一个包根目录，再执行对应命令；脚本识别这里成对设置的 host/guest 环境路径，并补齐临时目录隔离。`<包根目录>` 必须替换为实际解压目录。测试数据保留在包下的 `test-users/`，请勿删除或上传。

房主窗口：

```bat
cd /d "<包根目录>"
set "APPDATA=%CD%\test-users\host\appdata"
set "LOCALAPPDATA=%CD%\test-users\host\localappdata"
if not exist "%APPDATA%" mkdir "%APPDATA%"
if not exist "%LOCALAPPDATA%" mkdir "%LOCALAPPDATA%"
client\START-CLIENT.cmd
```

客机窗口：

```bat
cd /d "<包根目录>"
set "APPDATA=%CD%\test-users\guest\appdata"
set "LOCALAPPDATA=%CD%\test-users\guest\localappdata"
if not exist "%APPDATA%" mkdir "%APPDATA%"
if not exist "%LOCALAPPDATA%" mkdir "%LOCALAPPDATA%"
client\START-CLIENT.cmd
```

1. 两边进入「开始游戏 → 联机大厅」，协议选「局域网」。分别填写不同的合法用户名和昵称；身份密钥由正常 UI 自动生成，不要手工复制。取消勾选「观战」。
2. 房主保持「自动保存对局」开启；电脑玩家数量设为 0，选择可容纳两名玩家的选人模式。双方端口相同（界面当前默认 `24680`）；房主在「高级设置 → 开放连接的网卡」填 `127.0.0.1`，点「创建局域网房间」。
3. 等房主显示已连接房间，客机地址填 `127.0.0.1`、相同端口，点「加入」。此模式无需房间码，最小测试可不设房间密码。
4. 房主打开内容按钮（当前可能显示「本局内容」或「分享我的内容」）。在「服务端批准条目」页保留包内默认条目，点「服务端校验并应用」；若切到本机内容页，按钮为「共享所选条目」或「校验并应用」，共享不等于采用。等采用完成；出现风险确认时先阅读，再决定是否「确认使用所选数据」。收起窗口不会取消后台检查。
5. 客机点「下载本局内容」；等待两边内容同步完成，再各点「准备」。房主点「开始选人」，有选择项的玩家用「选择御主」完成选择；选人完成后房主点「进入对局」。按钮不可用时先看状态文字/按钮提示，不反复点击或重启。

若在认证、建房、内容采用或进入对局处停住，记下第一个错误和操作步骤即可；本说明没有宣称这条完整链路已通过真人验收。

## 保存与正常退出

- 大厅「自动保存对局」默认开启；当前联机没有单独的手动「保存」按钮。局域网对局实际由房主的权威子进程录制，目录为 `user://authority_rooms/<房间目录>/matches/<对局目录>/match.log`。上述房主命令或双击脚本选择 `host` 时对应 `test-users/host/appdata/FateDomination/authority_rooms/`；双击脚本选择 `guest` 时，`user://` 位于 `test-users/guest/appdata/FateDomination/`。不要直接双击 EXE 绕过隔离。
- 不要把大厅存档选择器初始打开的 `user://match_saves/` 当作所有局域网存档的实际落点。需要试恢复时，在「从存档继续」中定位原存档的 `match.log`，按 UI 指定座位；需要原身份与本机认证元数据，不能只凭昵称恢复。本包恢复链路仍待最终包验证，既不承诺成功，也不据旧报告认定失败。
- 默认保留存档；自动清理默认关闭。不要手工删除身份、房间目录或保存中的临时文件；「清理联机缓存」不是保存或备份。
- 大厅退出房间用「离开房间」。对局中先关掉卡牌/日志等浮层，再按 Esc 打开暂停菜单，选择「退出游戏」；「返回主菜单」提示会作废本局进度，不是保存按钮。暂停菜单只暂停本地界面，不暂停权威规则。
- 客机先退出，房主最后退出；等正常退出完成。**不要强杀正在保存/恢复/关闭中的实例或权威子进程**。无法确认是否保存完成时保留现场并反馈，不把窗口关闭当作保存成功凭证。

## 独立服务：仅部署者需要

在包根目录的 CMD 执行。部署者须先审核并准备 `server/server.cfg` 和 `signaling/signaling.json`（仅启动所需角色）；脚本固定读取 EXE 同目录的对应配置，不接受命令行参数。不要猜地址或端口，配置中的输出路径也须落在批准的隔离目录：

```bat
server\START-SERVER.cmd
signaling\START-SIGNALING.cmd
```

游戏服务客户端选「服务器」，按部署者给出的地址、端口创建/加入；信令客户端选「房间码直连」，使用部署者提供的连接服务地址与房间码。纯信令配置必须显式 `roles=["relay"]`，不可拿游戏服务配置直接替代。独立游戏服务正常停机用管理控制台的 `stop`，等待保存和关闭完成；不要强杀。

## 已知限制与反馈

以下仅为当前可核对的边界，**待最终包更新**：全量 `NOTRUN`；正式 GUI 双客户端创建/加入及完整对局 `NOTRUN`；真实保存恢复和独立 authority worker 就绪仍为 `UNKNOWN`，均未证实为失败，也未证实为通过；多机跨网 `NOTRUN`。本工具不证明新 native production DLL 已推广，只核对 manifest 绑定的实际文件。

包内 `known-limitations.json` 各限制项使用 `id/status/scope/evidence`；阶段结果以对应包的原始回执为准。`client-startup` 即便 PASS 也只表示启动冒烟，不是联机验收；专项绿只表示对应分支已验，整包仍待验。没有 full 回执时保持 `full_suite: NOTRUN`，`source_pass/release_pass: NOT_GRANTED`、`ready_token: NOT_ISSUED`，不能把静态校验、旧轮次或未运行项写成通过。

**逐项限制说明**：下面列出 12 项专项限制的现象、触发条件、预期与绕行；上面的整体 `NOTRUN`/`UNKNOWN` 边界继续有效，此处不重复。**本包用于受控玩法/交互诊断，不作为规则验收。** 下文的“未证实”不等于已失败或已通过。

### 1. G01：独立精确允许集合与隐私门缺口

- **现象**：独立精确允许集合尚未被完整消费；合成包中的普通 `credentials.txt` 曾通过，新增 `probe.log` 会被拒绝；PCK 策略和专用 external-native 信令消费者也存在缺口，G01 保持 `BLOCK`。
- **触发**：包中出现未命中 deny 的额外载荷，或把 manifest/ZIP 读回成功理解为所有载荷均获批准且无秘密。不要为了复现向交付包添加文件。
- **预期**：允许集合之外的未知载荷应被拒绝；PCK 与所用信令布局应由对应消费者审核。路径和 SHA 相等不足以证明内容无秘密。
- **绕行**：没有已证的玩家侧绕行。保持 ZIP 原样，不把身份、凭据或私人存档作为反馈附件；是否开展有限测试由责任人另行裁定，不能用阅读本说明解除 G01。

### 2. G04：未开局大厅保存不等于活局保存

- **现象**：正式 server 阶段曾认证建房，但 fixture 在开局前结束；关闭回执为 `saved=false, room_state_saved=true`，未取得对局保存成功证据。
- **触发**：只建房、未选人入局即关闭，或仅凭阶段 PASS/房间状态文件存在判断保存成功。
- **预期**：建议验收证据应包含两个已认证非观战网络成员、AI=0、同局开局、至少一次成功玩家命令造成真实规则变化，并在仍为 playing 且非终局时取得同实例最终 `saved=true`、日志读回及正常关闭证据；这是建议验收范围，不改变游戏最低人数规则，也不覆盖最终客户端 GUI 或完整恢复链。
- **绕行**：不要把 `room_state_saved=true`、关窗或返回菜单当作对局已保存。按包内流程观察，停住时保留首个错误；没有证据就记为“活局保存未证”，保留身份与存档，不依赖该候选承载不可替代的进度。

### 3. F16：恢复断线的根因仍未知

- **现象**：恢复链已有断线记录；现有公共事件不足以可靠区分 timeout、主动 close、本地 reset/inactive sweep 或 socket fatal。
- **触发**：恢复或续局时遇到连接中断，随后仅凭 `peer_disconnected` 等公共事件或其 data 给断线定因。
- **预期**：正常链应完成连接与续局；要认定根因，须取得对应冻结、实例和断线前分支证据。一次成功也不能证明间歇问题已修复。
- **绕行**：没有已证的恢复绕行。记录首次断线步骤与脱敏错误，保留原身份、存档及证据；不要自行调 timeout、加自动重试、换引擎或清理身份来“转绿”。

### 4. B24_unknown_summary：33 项玩家主体语义未闭合

- **现象**：33 项主体来源、成员/会话契约与覆盖范围未闭合，其中 31 项建议必须消解，U033/U043 仅为条件豁免候选；魔力消耗查询存在创建默认余额玩家条目的静态实现冲突，可能影响规则或权威状态。未证实这 33 项均为正常流程故障，也未证实与客户端崩溃存在直接因果。
- **触发**：缺失或旧会话 ID 进入创建式 getter；跨等待后主体已失效，或同 ID 已换成新局主体；外来数据或相关调试入口开放也会超出两项候选豁免的限定范围。
- **预期**：调用主体应有合法成员来源，并在读取/续行时仍属同局；魔力消耗查询不应因未知主体而写库。未知主体应拒绝还是 no-op 的完整政策尚待确认，本说明不另定政策。
- **绕行**：没有已证的玩家侧补救。固定内容、不碰调试只能减少暴露，不能证明入口不可达，也不能授予 U033/U043 豁免；须由责任人消解证据或明确风险裁定。

### 5. debug_release_reachability：单机调试入口静态可达

- **现象**：client/server PCK 含调试控制台资源；同冻结 v2 场景存在单机物理 `~`/反引号所在键的启用路径，未见 release 门禁。联机有门禁，但联机也能打开尚未证实。
- **触发**：单机 v2 中按下对应物理键并走到启用/切换面板路径；本项尚未做真实窗口按键复现。
- **预期**：正常玩法结果应与调试干预分开；静态可达不等于调试功能完整可用或窗口验收通过，也不能据此认定发布包入口已关闭。
- **绕行**：不要用调试面板补进度、改资源或制造验收结果。若误入或出现调试干预，记录并标明受影响样本，不把它当正常玩法证据；仅仅不使用该入口不能闭合门禁风险。

### 6. registry_b31_remaining：原七站只迁验两站，余五站未迁验

- **现象**：指定证据时点，B31 原七站中仅 RefillHand/RestoreLocationBenefits 两站有迁移终态；RegisterObjectEffects、RemoveFromBoard、DiscardPlayedCards、SyncPower、ChangePlOrder 余五站未迁验。未证实这些动作没有实现，也未证实直连本身就是玩法故障。
- **触发**：开局注册效果、回合收尾移出、清理已出牌、同步威力或轮换顺位涉及上述站点；把两站专项绿或后续仓库落盘当成旧包七站完成会误判。
- **预期**：七站应逐站取得对应业务敏感性、恢复及同冻结证据；两站报告不能代表全部七站。后续迁移落地须重新冻结组包，不能自动写入当前 ZIP。
- **绕行**：没有玩家侧迁移绕行。可以记录正常流程观察，但按实际站点和当前 ZIP 标注，不能用“这局没出错”签署七站迁移通过，也不以绕过回合收尾冒充验收。

### 7. A9_payment_forecast：支付魔力消耗可能改变移动可进入性

- **现象**：支付会派发效果链，可能改变落点合法性；公共零副作用整链 forecast 尚不足以可信覆盖“支付后禁入”。已有先付后移政策不能当作实现已验。
- **触发**：移动支付监听改变资源、禁入或其他可进入条件；只在付款前查看可进入提示，或只迁路由而沿用旧次序，都可能造成结果误判。
- **预期**：遵循既有先付后移规则，并能在批准支持域内无活体副作用地测算支付链及支付后的可进入性；不擅自把“先移后付”旧次序当作该规则通过。
- **绕行**：没有已证的无损绕行。涉及支付改变可进入性的场景要单独标记并保留动作前后观察，不能以一个绿色提示判定合法；不要通过改资源、移除监听或调试移动来凑通过。

### 8. D4_atomicity：支付拒绝后的规则事实撤销未闭合

- **现象**：来源静态顺序是先记选项用量、来源层数、chosen 与 option_used，再支付；支付拒绝点没有完整撤销这些事实。展示事务 abort 或事务归属 token 不等于规则对象图已回滚；D1 登记补偿/D5 队列绿也不证明 D4。
- **触发**：普通非延迟选项已登记用量等事实后，魔力消耗支付被拒绝，或相关监听使复核失败。
- **预期**：拒绝应具备本次尝试范围内的失败原子性，不能留下本次不应消耗的用量、层数、chosen、规则日志，同时不能撤掉此前父动作；所需作用域与 savepoint 尚待闭合。
- **绕行**：没有已证的局部撤销绕行。拒付后记录用量、层数与选择状态是否变化，不连续重试掩盖首个异常，也不靠手工回改或调试撤销证明原子性；暂停/恢复等策略需组织者确认。

### 9. performance_fixture_boundary：夹具预算验敏，产品性能改善未证实

- **现象**：夹具预算改为 420 秒，并完成 420→60→420 验敏；三轮各保留 62 CHECK，exit 0→1→0，60 秒唯一红是预算终局断言。该结果仅说明验敏边界，未证实产品性能改善或 60 秒达标。
- **触发**：把放宽夹具后的绿解释为游戏更快，或沿用旧的“60 秒门仍欠验”结论。注入轮真实跑至自然终局；60 秒项的红来自预算终局断言。
- **预期**：按各自明确的夹具预算判读验敏，性能评价另取同冻结证据；不能把 420 秒夹具预算当作玩家应等待的产品承诺，间歇恢复断线仍单列。
- **绕行**：本项不需玩家绕行。测试时记录实际等待与步骤，不把 420 秒预算当作产品时限，也不把成功三次当作 F16 已修复。

### 10. local_spell_window_and_tail：令咒卡条真实输入与后段未验

- **现象**：本人令咒卡条悬浮展开、命中区、刷新保持的四条 headless 红已有环境因果；同冻结真实 OS 窗口输入及具体导出包仍未验。第四条早退使后续滚轮、特殊卡点击、取消不扣魔力消耗、离开收起未执行。
- **触发**：相关悬浮、滚轮、特殊卡点击、取消或离开交互；旧 headless 测试的鼠标 warp 未更新生产读取位置时出现红，真实硬件鼠标是否同样受影响尚未证实。
- **预期**：应在同冻结窗口/OS 输入层核验展开与命中、刷新、滚轮/点击、取消不扣魔力消耗和离开收起；Viewport 合成输入及旧窗口绿不能替代这一层次。
- **绕行**：没有已证的交互替代。只记录实际能否操作，停住时保留首个现象；不得将未运行的后段标为通过，也不以反复连点或调试调用作为正常点击成功证据。

### 11. ui_gold_frame：金框不严格等于常规出牌合法
