# 联机清单与底层分帧实施进度

## 本批已修改并验证

- `room_manifest_transfer.gd` 按实际 Variant 编码拆分超过单消息预算的批准文件清单；小清单保留原消息格式。
- 接收逐片校验版本、总数量、连续偏移、单片大小和累计清单预算。整份收齐后再次复用 `RoomDataAssembler.validate` 检查跨片重复路径及目录前缀冲突，才替换当前清单与版本；失败保留上一份完整清单。
- 清单累计预算、无进展时间和既有文件/数量预算明确配置，不通过分片取消限制。离开、断线和重连释放半成品；收齐清单不冒充素材安装或版本确认。
- 真实 WebRTC 大清单测试先复现原生插件 `Message size exceeds limit`。`packet_fragments.gd` 在可靠传输层透明分帧：应用层仍限制整消息大小，WebRTC 底层帧使用显式预算，收齐后才解码与交付；清单、快照及原有文件块共用，不复制 P2P 专属业务协议。
- 分帧按真实来源与可靠通道隔离，校验序号、连续偏移和总长度，限制总预留与并发数量；超时、拒绝和断线回收预算。仍禁止网络 Object/Callable、递归分帧和应用自报保留帧标记。
- `max_webrtc_frame_bytes` 默认 16384，对齐已安装 webrtc-native 1.2.2-stable 数据通道源码的声明；不是从消息内容推断。Godot C++ 的 `get_max_packet_size` 未绑定为此处可调用的 GDScript API，不使用不存在的公开方法。
- 分帧计算包括 Variant 的四字节补齐，专项使用非四倍数预算并逐帧核对实际编码长度。
- 服务端网关将完整清单和清单分片归入同一可靠素材通道。此调整仅属于独立服务端转发，未将 P2P 信令改成游戏流量中继。

## 提供者候选目录分片

- `catalog_message_transfer.gd` 复用 `MatchPacketFragments`，仅为 `catalog` 与 `server_data_catalog` 提供独立累计消息预算，不增加普通对局消息上限。小目录保留原格式，单个大条目也可分片。
- 上传使用 `catalog_part` 和原请求通道；服务端回传使用 `server_data_catalog_part` 和原素材通道。网关按两个明确消息种类转发，不混淆请求序号和数据回执顺序。
- 接收前检查大厅阶段与实际连接资格，按连接隔离缓冲，收齐后禁用 Object 解码并检查基础类型和预期方向，再走原序号及条目指纹校验。首片、错误末片、预算不足、超时或掉线不替换旧完整目录；普通未分片目录同样遵守累计预算。
- 已完整接收且独立校验的批准请求副本，不因提供者掉线、撤回目录或候选目录刷新失效；请求取消、房主资格与大厅阶段仍独立校验。对局已采用数据保持主机固定副本，不从提供者实时读取。
- `tests/runtime_reports/catalog_fragment_regression/verified-summary.json`：9 套、149 条断言，退出码、RESULT 和引擎错误已程序对账。包含两位真实 ENet/P2P 提供者交错上传、首片后掉线和超时，真实公开网关超 1 MiB 目录双向分片及批准分发，掉线后批准、撤回后批准，以及服务端非 headless 完整终局；终局截图已原生检查。
- 测试缓存与输出可按用户要求清理；上述结果是实际执行记录，历史报告路径不保证清理后仍存在。
