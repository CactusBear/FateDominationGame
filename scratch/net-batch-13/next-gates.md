# net-batch-13：恢复后数据屏障与身份恢复下一轮门槛

## 结论、范围与证据等级

**可直接推进的是恢复提交门槛、身份落盘/票据交付顺序、数据确认回执及其反例；不能用大厅恢复、worker READY 或自动脚本通过代替原局恢复及真人验收。**

本轮只读当前源码与既有计划，仅新增本文件；未运行 Godot（含导入、场景、导出）、未修改生产代码、未读取真实凭证、未操作进程。所有缺口为静态确认或明确列出的待核实风险，不是动态复现。共享工作树可能继续变化，主代理实施前须复核实际 diff。

来源：`docs/acceptance-root-authority-identity-audit.md`、`scratch/net-batch-12/data-barrier.md`、`scratch/net-batch-12/next-gates.md`、`docs/real-world-multiplayer-test-plan.md`、`docs/lan-multi-machine-test-plan.md`、`docs/cross-network-p2p-test-plan.md`。源码行号仅指本次读取快照。

固定拓扑：信令面只交换 SDP/ICE、辅助打洞；LAN/P2P 游戏数据直连房主，dedicated 经服务端网关路由至 worker；规则与存档权威位于房主机器或独立服务端机器，不随管理房主转让迁移。信令不得转发游戏流量、计算规则或保存对局；真人掉线不交 AI。

## P0：原局恢复与权限提交必须失败关闭

### P0-R1 恢复完成闸门未重新验证全部原真人在线

- **静态确认**：`server_room_worker.gd:225–235` 在开始恢复前检查 `_recovery_bindings` 指向成员在线；但 `lobby_session.gd:380–383` 将恢复转为 playing 的条件仅是 `match_authority.started && data_ready()`。`data_ready():1032–1040` 只遍历 connected 成员，因此真人在异步恢复/等待数据时再次离线，会被屏障排除。常规推进已有 `_disconnected_players()` 闸门（378 行），不等于恢复相位提交具备同一不变量。
- **直接修复**：复用稳定 player→member 绑定、断线检查与认证上下文，在恢复提交点再次验证全部原真人绑定仍有效、已认证且在线，并确认各自当前恢复数据版本。把 restoring→playing 收敛到同一个显式提交入口；不要修改普通 data_ready 的所有语义或把离线真人改为 AI。保存管理暂停语义，数据通过也不自动解除管理暂停。
- **红→绿门槛**：全部原真人重连后开始恢复，在 replay await/清单发布/最后 ACK 前分别断开一人；其他人 ACK 全齐也必须保持 restoring，原待答和资源不变。合法原身份再次重连、确认新版本后才能提交一次；重放旧 ACK/旧连接/旧实例不解锁。复核后续命令拒绝和自动 step 均不能越过该闸门。

### P0-R2 共享恢复失败不是原状态不变的事务

- **静态确认**：`lobby_session.gd:1374–1425` 恢复前即修改 phase/revision 并 `_publish()`；失败分支将 phase 设成 lobby，而非还原原 restoring/大厅快照。成功候选回放后又逐文件 `publish_blob`，全部检查尚未完成即可能留下可见字节；最后替换 match_authority、清视图、提交清单，未见该入口要求恢复状态持久化成功后才返回 true。不能据此断言所有故障都会破坏规则，但“失败旧状态不变”当前入口没有闭合契约。
- **直接修复**：复用现有检查点、候选 authority、RoomAssets 校验与安全文件替换，拆 prepare/commit/abort。先在隔离候选内验证存档/全部数据/绑定，保存完整前态；持久化提交后才替换活动 authority、规则目录、清单/修订与视图，发布一次。失败保留原档、原房间相位、绑定、数据与权限；不能完整回退则停在明确恢复失败/暂停状态，不宣称已恢复或可继续。异步期间绑定 room/instance/恢复请求，防止原房间被关闭或替换后提交。
- **红→绿门槛**：在 replay、复制、文件哈希、assets.install、恢复状态写/flush/替换及最终发布分别失败，逐字段/逐字节比较旧状态；已追加日志不能用内存回滚假装回卷。正常路径先保存→新实例→逐文件校验→原真人认证重连→候选回放→当前数据屏障→恢复提交→同中局继续一次、不重复扣费。
- **不可绕开**：`authority_host_client.gd:102–109` 与 worker:227–230 已显式阻断 LAN/P2P 存档恢复。安全契约未闭合前保留 BLOCKED，不删除阻断或改模式骗绿。

### P0-I1 普通身份恢复先交付新票据，忽略持久化失败

- **静态确认**：`lobby_session.gd:244–252` `_accept_identity()` 先建立 peer/member 路由、轮换哈希、发 identity，再调用 `_persist_recovery_state()` 且不检查返回值；`_join_identity():283–289` 已修改 reconnect/join/密钥绑定后仍返回成功。相比之下 `_inherit_identity():329–338` 已在保存失败时回退身份区块；不要把这两个入口混为同一实现。
- **直接修复**：对要求持久化恢复的房间复用身份事务准备及快照回退：先保存新成员/连接资格/绑定/哈希候选，再提交内存并交付票据；保存失败不认领席位、不更新修订、不发成功身份，不推进 restoring。显式区分无恢复文件的兼容模式，不能让其因 `_persist` 返回 false 全部入房失败。核对 Windows 原子覆盖，失败不先删原档。
- **红→绿门槛**：首次入房、原身份重连轮换、identity_ack 淘汰 previous 各注入写/flush/替换失败；旧档哈希、旧权限/路由/凭据及恢复绑定保持一致。发送失败必须有明确终态，不能自动撤销已落盘授权或重复执行恢复动作。真正盘故障另在隔离测试卷验，不填满用户盘。

### P0-D1 恢复/候选内容未受当前批准清单的下发授权约束

- **证据**：batch-12 DB-01；本轮共享恢复:1399–1405 同样逐个 publish 后才检查全集。准备任务与 worker 初始候选池应随实际生产 diff 重新核对；不把旧审计行号当新代码结论。
- **直接修复**：隔离候选字节；权威下发 `_queue_blob` 按当前已批准 room_files 哈希集合授权，上传服务单独保留提供者授权。取消、拒绝、恢复 abort 或换版后旧候选不得被在线成员按已知 hash 取走。不得靠未知 hash 难猜解释成安全。
- **红→绿门槛**：普通成员请求未批准、取消、失败恢复部分发布及旧版本 hash 均拒绝；当前批准 hash 正常传输。身份恢复成功但数据屏障未过，不能先发布私有对局视图或开放规则动作。

- 当前 `load_recovery_state():1314–1316` 使用 valid_state；错认证密钥先于票据认领检查（278–281）。保留这些拒绝；认证旧档缺绑定失败关闭，不能由首个持票者/昵称建立绑定。未认证兼容与显式管理员迁移需分别验，不擅自全禁兼容。
- worker 先读取旧恢复状态再启用其持久化路径（155–164）；已有隔离目录逐文件验证（133–144）。不再报“host 初始化必然覆盖旧恢复文件”，但仍需动态崩溃原档对照。
- audit 文档里通用 MatchJournal 格式与业务审计接线是两回事。batch-12 已有审计/开局失败证据，本轮不重复归因为 card_id 负数；身份审计、规则事务审计和规则日志分别对账。
