- 本文件依据当前源码、`docs/package-real-test-checklist.md`、`docs/real-world-multiplayer-test-plan.md`，并复核 batch-10 旧结论。仅写本交接文件；未运行 Godot、服务端或导出，未接触凭证。所有代码结论均为静态确认，不能填运行 PASS。

## A. 主代理当前可直接修的 P0/P1

### P1-1（本批首先处理）：房间启动回执没有闭合请求关联与终态

**证据**

- `server_room_manager.gd:190–196`：spawn 后登记 `ready=false` 即返回 room_id。返回 ID 只说明启动请求受理，不是房间 ready；`poll():223–235` 后续才验证 ready 报告/处理启动超时。
- `server_gateway.gd:164–173`：异步 `_pending`、`_creators` 仅保存实例绑定/peer，没有保存创建请求 seq。`poll():61–74` 的异步失败调用 `_fail()` 时未传原请求；`87` 的 `server_attached` 仅带 room/peer_id，不含原请求编号及实例关联。
- `lobby_session.gd:374–377`：先置 `_server_sent=true`，随后发列表和建房/加入，未检查发送结果，也未通过现有 `request(..., registered)` 记录这次操作的序号。`563–568` 接受附着时只检查 room/peer_id 类型，没有与 pending 操作关联。
- 网关 `_fail():410` 使用 `request_seq`；客户端错误消费 `lobby_session.gd:657–664` 只读取 `seq` 来发 `request_rejected`。因此即使同步拒绝带关联号，客户端也不能按现有契约关闭指定 pending 请求。
- `server_console_channel.gd:185–194` 的建房回执已经明确 `status=pending, ready=false`，这一点是正确语义；但 `room_info:196–199` 的查询只返回部分字段，尚未给出完整启动请求/实例终态对账契约。不要把该 pending 改为即时 ready。

**直接修复**

1. 复用 `request` 的 registered 回调及 manager 实例绑定，不另建一套 room manager。显式保存请求序号/动作、room/PID/instance_id/authority_host_mode；本机管理回执与网络回执使用各自稳定请求标识，不混用控制文件 request_id 与网络 seq。
2. 对齐网关与客户端的拒绝关联字段；同步提交失败、异步启动失败/超时、路由失败、实例更换均结束对应 pending，并保留可查询结果。传输入队失败必须报“提交未确认”，不能假报未执行，更不能自动重发建房。
3. 分开呈现“启动已受理”“worker 已就绪”“路由已附着”“成员已加入”。ready 必须由 manager 的实例报告和进程所有权验证确认；server_attached 不等于玩家 join 完成，更不等于开局成功。
4. 客户端只接受当前连接、当前请求和预期房间的回执；旧实例、重复终态、乱序回执不得修改新请求。断线/场景退出清理本端 pending，但不擅自删除服务器恢复登记或杀未保存 worker。
5. 控制台保留 pending 查询语义，补完整实例字段与明确终态查询；失败目录/本次独立日志保留，不把房间编号存在或旧 ready 文件当成功。

**补夹具（本轮不执行）**：spawn 失败、有效 ready、坏/旧 ready、ready 后路由失败、超时、创建者断线、同一连接重复请求、两房间隔离、旧请求晚到、发送失败、`request_seq/seq` 兼容消费。既有 `net_server_cli_test`、`net_member_identity_binding_test` 只可复用为起点，不能凭其中收到 server_attached 宣称启动回执全覆盖。

**对应真人门槛**：RW04/RW08、包清单“两客户端建房/加入/直连”与本次 room 实例日志；代码闭环后仍须真人从正式入口建房、加入和开始选人。

### P0-1：本机安全关闭回执匹配了清空后的 room_id

**证据**：`authority_host_client.gd:126–138` 保存 `_closing_target` 后清空 `room_id`；`152` 仍将 response.room 与空 room_id 比较。正常拒绝回执因此被忽略。

**直接修复**：按保存的关闭绑定匹配 room/PID/instance/mode，并保存请求 ID 校验；分开处理提交失败、拒绝、成功回执及 OS 所有权确认退出。重复 close 不覆盖正在排空的请求；提交失败可观察，不能超时杀未保存 worker。复用现有进程所有权接口，裸 `OS.is_process_running` 不能证明是原实例。

**补夹具**：保存后关闭、未录制拒绝、写请求失败、重复 close、旧实例/旧请求、UI 场景退出后排空及其他房间不受影响。真人对应 RW16/RW23/RW24；拒绝原因必须在可见交付渠道保留，不能只在已经退出的窗口提示。

### P0-2：恢复状态与配置覆盖写入的失败原子性

**证据**：`lobby_session.gd:1365`、`server_room_manager.gd:117` 仍以临时文件加 `DirAccess.rename_absolute()` 覆盖目标。此静态事实不能证明 Windows 覆盖替换安全；现有 `legacy_identity_migration.gd` 有平台安全替换与原字节保留路径可复用。

**直接修复**：提取/复用已有可信本机路径替换能力，区分首次建立与已有目标替换，检查写入/flush/替换结果。失败保留旧档及旧内存状态，不提前发布新密码、暂停、继承或恢复成功。不能先删旧文件，也不能将 `.tmp` 写入成功当提交成功。

**补夹具**：已有档替换失败、权限/flush 失败、并发变更、首次建立失败；逐字节核对旧档，沿保存/密码/继承/恢复调用链验证。Windows 实际失败行为、原局恢复仍留 RW17–19/RW23–24，不以静态解析代替。

### P1-2：录制开关与存档能力 UI 沿用旧同进程房主判据

**证据**：`lobby_screen.gd:63–64` 仅改本地 `session.record_matches`；`authority_host_client.gd:34` 只在创建前复制给 manager。大厅 Archives 可见/恢复资格 `lobby_screen.gd:498–500` 仍按 `session._host`，而新本机房主 UI 是 worker 客户端。`authority_host_client.gd:104–117` 明确安全阻断恢复并报告 unavailable。

**直接修复**：先将现状兑现为明确 UI 契约：建房后固定的录制设置禁止本地伪切换，显示实际权威录制值/目录与恢复不可用原因；管理房主资格与规则执行资格分离。若实现大厅可改录制，则走现有实例绑定管理请求、落盘成功及权威回读，失败保持原值。恢复按钮不能通过把 `_host` 改真或直接取消阻断来启用。

**补夹具**：建房前设置、建房后禁用/已确认修改、管理房主转让、日志实际产生、不可用提示。对应 RW15/RW23，不把日志文件存在当完整保存。

### P1-3：建房前密码输入与实际保护状态不一致，先修提示/入口

**证据**：创建入口没有把 RoomPassword.Input 传入 manager 的权威创建事务；该输入用于 join 或进入大厅后 `room_password` 操作。当前“默认新房无密码”符合 RW05，但预填不能代表建房即受保护。

**直接修复**：区分“加入密码”与“大厅设置密码”，建房前明确提示需进入大厅由房主设置，状态只读权威 `password_required`。本批不将口令塞普通 settings/命令行/公开快照，不顺手宣称已完成保密传输或受保护初始化事务。

**补夹具/真人**：预填后建房仍显示真实无密码；房主设置/清空后回读；客机越权拒绝。真人执行 RW05；ENet 的保密通道/KDF/抗猜测能力需独立实施与抓包验证，提示修复不关闭安全缺口。
